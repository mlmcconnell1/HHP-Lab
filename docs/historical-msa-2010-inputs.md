# Historical MSA inputs for calendar year 2010

## Recommended reference

For a historical comparison representing areas in effect during calendar year 2010, use the December 1, 2009 OMB update, OMB Bulletin 10-02, and the matching December 2009 Census CBSA county-component list. OMB says Bulletin 10-02 took effect immediately, was the final update before the 2010 Census, and applied the 2000 standards to Census 2000 data plus Census Bureau population estimates for 2007 and 2008. The 2010-standards delineation came later; Census reports that areas based on the 2010 standards and Census data were delineated in February 2013.

Keep these dates separate in implementation and provenance:

| Fact | Value |
|---|---|
| Definition source release / OMB effective date | 2009-12-01 |
| Calendar year represented by that effective definition | 2010 |
| Standards and data basis | OMB 2000 standards; Census 2000 and 2007/2008 population estimates |
| Boundary geometry and county-equivalent identifier vintage | 2010 TIGER/Line; county entities and names as of 2010-01-01 |
| Later 2010-standards delineation | February 2013; do not substitute for a 2010 in-effect comparison |

The OMB bulletin is the authority for the effective definition and area classification. The Census December 2009 workbook is the machine-readable county-component source. A version label such as `census_msa_2010` can continue to mean “definition used for calendar year 2010,” but provenance must also store the exact source release date (`2009-12-01`) and standards basis. Do not call the source a “2010 delineation file”; the actual historical file is dated December 2009.

## Metropolitan areas, micropolitan areas, and divisions

List 3 is titled “Core Based Statistical Areas (CBSAs) and Combined Statistical Areas (CSAs), December 2009.” Its `Status, 1=metro 2=micro` field is the explicit class discriminator. The inspected workbook contains 374 metropolitan statistical areas (1,168 county/equivalent component rows) and 581 micropolitan statistical areas (694 component rows). All 1,862 component rows have status 1 or 2; there are no duplicate MSA/county pairs or CBSA codes classified as both metro and micro.

Use status `1` to construct the MSA definitions and county membership. Exclude status `2` from MSA outputs; those records are micropolitan areas, not small MSAs. Do not interpret the workbook's CSA columns or titles as MSAs either. The workbook records metropolitan division code/title on component rows: 11 MSA parent codes contain 29 distinct division codes. Divisions are subdivisions inside qualifying large MSAs, not replacement CBSA/MSA IDs. Keep the parent `CBSA Code` as `msa_id`; do not count divisions as additional MSAs. The current MSA artifact contract does not represent divisions separately. If a later consumer needs divisions, expose them as a distinct geography/product or add explicit division fields without changing the parent-MSA identity.

## Inspection results and county identity

The 2010 TIGER county layer contains 3,221 unique `GEOID10` county/equivalent records. All 1,168 MSA county-equivalent FIPS values from List 3 occur in that layer, and all 1,168 MSA county-to-CBSA assignments match its `CBSAFP10`; no MSA rows or assignments are missing or mismatched. TIGER 2010 documentation describes these county/equivalent boundaries and names as of January 1, 2010 and defines `GEOID10` as the concatenation of state and county FIPS. The county layer exposes `GEOID10` and `CBSAFP10`, but does not carry the MSA/micropolitan status field; retain List 3's status as the authoritative type discriminator.

Use five-character FIPS strings as keys. List 3's `Component Name` includes qualifiers such as `County`, `Parish`, `Borough`, `Municipio`, and `city`; TIGER's `NAME10` generally omits those labels. Name comparison therefore is not a safe join. The county-equivalent distinction matters especially for Virginia independent cities and Baltimore City and St. Louis City, whose separate FIPS identities must not be collapsed into similarly named counties. Preserve the source component name for reporting and use FIPS for joins. Puerto Rico municipio FIPS are also present and should remain strings with leading zeroes preserved.

The county FIPS inventory aligns exactly with the 2010 TIGER county vintage for MSA rows. For data carrying a different county vintage, do not infer equivalence from a matching county name; use the relevant Census county relationship/crosswalk where entity boundaries or identifiers changed. For 2010 geography joins or dissolves, the exact needed file is the 2010 TIGER county/equivalent layer included here, not the modern 2020/2023 CBSA boundaries. The 2009 OMB membership defines which 2010 county equivalents belong to each parent MSA.

## Implementation plan for the existing MSA ingest

Current `hhplab/geographies/msa/msa_definitions.py` is specific to the July 2023 `.xlsx`: global constants identify `census_msa_2023`, the 2023 workbook filename, a fixed 2023 source label/ref, 2023 column names, `header=2`, and exact string filtering on `Metropolitan Statistical Area`. `msa_io.py` hardcodes the one 2023 URL/name in download, source registration and provenance. The 2023 geometry CLI also defaults the TIGER boundary year from `DELINEATION_FILE_YEAR`, conflating the delineation-file date with geometry vintage. `msa_coc_panel.py` infers county vintage from any four-digit year in the version string, which is too implicit for a source dated 2009 but aligned to 2010 county entities.

The follow-on implementation should:

1. Add a version-keyed source specification for the 2023 workbook and the December 2009 `.xls`, with separate fields for source release/effective date, definition version, file format/header row, raw filename, area-type/status mapping, county boundary vintage, and source URLs. Keep the existing 2023 configuration unchanged.
2. Add a parser for List 3's 12 columns and legacy workbook header placement. Map `CBSA Code` to the parent `cbsa_code`/`msa_id`, `CBSA Title` to the name, status `1` to `Metropolitan Statistical Area`, component name/state/FIPS/county status to the current standardized membership fields, and preserve five-digit identifiers as strings. Verify `Level of CBSA` is consistent with status. Reject unknown status values.
3. Keep only status-1 parent MSAs in the current MSA definitions and membership products. Keep status-2 micropolitan areas out. Keep division codes/titles subordinate to their parent CBSA; do not expand the existing MSA row contract with divisions unless a separate division product is approved by the implementation owner.
4. Separate the historical source's Dec 2009 release from the 2010 county geometry vintage in raw snapshots, provenance, source registration, and CLI defaults. Avoid deriving geometry year from a string that contains the publication year; resolve it from the versioned source specification or explicit parameter.
5. Reuse current normalized output columns and validators for definitions and MSA-to-county membership. Validate unique five-digit `msa_id`/`cbsa_code`, unique `(msa_id, county_fips)`, only metropolitan `area_type`, and expected counts (374 areas / 1,168 memberships) from this frozen source. If storing division details, add a separate explicit schema and validation rather than calling each division an MSA.
6. For historical boundary polygons, use the 2010 TIGER county/equivalent shapes and dissolve counties using the historical membership (or verify any CBSA polygon source against those county pairs). Do not download 2009 TIGER with the 2009 delineation date: definition release and geometry vintage are distinct. Preserve county equivalents and test all FIPS against `GEOID10`.
7. Add focused tests using captured List 3-shaped fixtures for the header/status/FIPS parser and a fixture with MSA divisions, then verify the real-source counts and membership against the checked-in output manifest during an explicit ingest/validation workflow. This input audit itself did not modify production code or curated data.
